# 喜餅與人情往來設計草案

日期：2026-09-06。狀態：第一版已實作、驗證並部署至 `/planner/gifts`，部署結果見 [改版進度](./改版進度.md)。

第一版實作：獨立送禮對象、多筆婚宴回覆連結、多款式與備用盒數、參考估價、交付與代領、宅配收到確認、誤登作廢、訂購成交價與修改歷史、廠商贈盒、唯一花費連結、沿用付款及附件、依用途 CSV 匯出。整批修改安排、物流追蹤、庫存調撥、紙本喜帖、禮金簿與線上幫手發餅未納入本次上線；下文保留後續設計方向。

使用者已確認的需求：喜餅要計入婚禮費用；未出席婚宴、甚至沒有填出席表單的親友，也需要能安排送餅。以下操作方式、第一版範圍與資料關係為建議，尚未視為使用者已逐項定案。用詞見 [婚禮籌備詞彙](../CONTEXT.md)。

## 設計原則

- 送禮對象獨立於出席回覆，不要求先建立一筆「不出席」回覆才能送餅。
- 以實際送禮單位登記，可是個人、一戶家庭或公司部門；盒數人工指定，不由出席人數、親友方或禮金自動推算。
- 送餅安排、喜餅訂購與付款各自記錄，畫面能互相連結。親友是否收到、廠商是否收款是兩件事。
- 既有廠商、花費、付款與文件繼續共用，喜餅模組不建立另一套獨立帳本。
- 款式可多筆；只有一款時自動帶入，常用盒數預設一盒，進階欄位按需展開。

## 後台入口與日常使用

新增「喜餅」入口，內有「送餅名單」「訂購與費用」兩個分頁。喜帖和禮金後續接同一份送禮對象，第一版先完成送餅與費用流程。

「送餅名單」上方呈現已確認需求盒數、另列待決定需求、待交付盒數、缺地址筆數及各款式訂購缺口。可篩選親友方、聯絡負責人、婚宴回覆、款式、交付方式與交付進度。

| 操作 | 行為 |
| --- | --- |
| 從賓客加入 | 選擇既有出席或不出席回覆，帶入稱呼與聯絡資訊，指定款式及盒數；再次加入已關聯回覆時開啟既有對象 |
| 新增送禮對象 | 填稱呼即可先存，例如「台中的阿姨」「公司行政部」；不建立出席紀錄，不影響婚宴人數和桌次 |
| 編輯送餅安排 | 指定一款或多款、每款盒數、負責人、預計交付日與方式；可標記仍待決定 |
| 批次安排 | 先選取對象，再套用款式、盒數、負責人或交付方式；顯示變更摘要，既有安排不因重複操作而加倍 |
| 記錄寄送／領取 | 輸入本次實際盒數，預設帶入尚未交付數量；可記收件人、代領人及備註 |
| 匯出 | 分別提供宅配清單、親送清單、現場領取清單、廠商各款式數量；各清單只含作業需要的欄位 |

手機名單每列突出對象、款式、尚欠盒數與下一個操作。地址、歷次紀錄、費用等次要資料放進明細，避免橫向大表難以操作。

## 送禮對象與出席的關係

送禮對象保存稱呼、個人／家庭／團體類型、親友方或自訂群組、主要聯絡人、電話、負責人及備註。宅配地址可稍後補；採宅配時才列為待處理事項。

送禮對象可以關聯零筆或多筆出席回覆。例如夫妻各自填表，但只送一份家庭喜餅，兩筆回覆可指向同一送禮對象。關聯只提供出席資訊參考，送餅盒數仍取自安排本身。

已有關聯時顯示對應回覆；沒有關聯時顯示「未關聯婚宴回覆」，不得直接標成「不出席」。多筆回覆狀態不同時展開列出，不壓成單一真假值。

同名、同電話或同地址只提示可能重複，不直接合併。新回覆日後可人工連結到原本僅送餅的對象；原有盒數、交付紀錄及收件地址保留。

出席改為不克，送餅安排保持原狀；若原本預計現場領取，提醒負責人改為宅配、親送或代領。取消出席回覆的關聯也不得連帶刪除送餅歷史。

## 盒數、訂購與庫存用詞

每種款式獨立統計，不把不同款式當成可互相替代的盒數。

| 數字 | 定義 |
| --- | --- |
| 已確認需求盒數 | 有效、已確認送餅安排的總盒數；包含已交付部分，不包括待決定及已取消安排 |
| 備用目標 | 希望額外預留的盒數，獨立於送禮對象 |
| 已訂可供盒數 | 已確認訂購的付費盒數加廠商贈盒，扣除已確認取消或不可用數量 |
| 訂購缺口 | max(0, 已確認需求盒數 + 備用目標 − 已訂可供盒數) |
| 已交出盒數 | 已有效寄出、親送或領取的數量，包含仍在運送中的包裹 |
| 待交付盒數 | 已確認需求盒數減已交出盒數；配送中另列，不能再次當作尚未寄送 |

廠商贈盒增加可供盒數，貨款為零。備用目標不是廠商贈盒，兩者不能混用。「已訂可供盒數」也不代表餅已到新人手上；訂購明細另記預計取貨／到貨日與實際到貨紀錄。

第一版不提供多倉庫調撥或自動物流追蹤。廠商直接宅配親友與新人先取貨再分送都可登記，前者不製造一筆虛構的新人到貨紀錄。若提供「手上現貨」數字，必須由實際到貨、親自交出與調整紀錄計算，不能以訂購總數代替。

## 交付與分次紀錄

交付方式為宅配、親送、婚宴領取；代收／代領是本次接收者資料，可搭配以上方式。一次交付可包含同一對象的多種款式與數量。

交付紀錄保存實際盒數、時間、經手人、收件或代領人、當次地址快照、配送單號及必要備註。寄送可以先標「已寄出」，人工確認後標「已收到」；未確認收件時仍保留寄送事實，避免重寄。

只領兩盒中的一盒，保留第一次紀錄並顯示還欠一盒。重複按送出或兩個人同時登記，必須由後端防止重複交付及數量超過安排；前端停用按鈕不足以保證正確。

已交付紀錄的修正需保留原因與前後內容。退件或毀損記錄為異常，由負責人確認是否重送；重送需要額外盒數時列為補寄需求，不抹去第一次寄出紀錄。取消安排不得把盒數降到已有有效交付數量以下。

## 訂購與費用

「訂購與費用」管理廠商、款式、各款付費盒數、廠商贈盒、成交單價、折扣、運費、其他費用、預計取貨日、訂單編號與合約／報價附件。價格及條件以本次廠商確認內容為準。

款式上的參考單價用於估算；每次訂購保存成交價快照。後來調整參考單價或加訂價格不同，既有訂購金額不跟著改變。

金額分開顯示：

1. 預算額：新人設定希望控制的金額，沿用既有花費預算。
2. 需求估算：依安排與備用需求、參考價格及估計費用計算。未確認的贈盒與折扣不當成確定優惠；尚缺款式或單價時標示估算不完整。
3. 確認訂購金額：各款付費盒數 × 本次成交單價，加本訂購負擔的運費及其他費用，減已確認折扣。
4. 已付金額：共用既有付款紀錄，只加總已付款項。
5. 尚欠金額：確認訂購金額減已付金額；已排未付分期與未安排付款的差額另外呈現。若變更造成溢付，顯示待對帳，不自動當成零或發起退款。

### 與現有記帳的連接

每筆喜餅訂購連到唯一一筆既有花費；確認訂購時可建立新花費，或選擇已手動登錄的同廠商喜餅花費。已被其他訂購使用的花費不可再次連結。訂金、尾款及附件沿用原有資料，重試建立不重複新增。

送禮對象不各自產生花費。交付、代領、改出席與修改需求盒數，都不自動更改已確認訂購金額。需求增加先提示缺口，再由新人記錄廠商確認的加訂；下單後不送某戶，也不自動當成廠商已退款。

已連結的合約金額從訂購明細維護，預算頁導回該訂購編輯；各頁讀取同一份金額，避免兩邊互相覆寫。既有手動花費金額與新訂購明細不一致時，先列出差異供核對，不直接覆蓋。

運費依實際訂單或寄送收費單位記錄，不以收禮人數或盒數固定相乘。廠商合約已含的運費只在該訂購計一次；新人另付物流的費用另連一筆物流花費，不能同時再加進喜餅合約。配送紀錄可引用該費用供查閱，引用不產生第二份支出。

目前 `Expense` 已有預算、合約金額，`Payment` 已有分期與實付日期；但現有 `unpaid_total` 是未付分期的加總。串接時需明確區分「尚欠合約金額」與「已安排未付」，避免只登記訂金後把未安排的尾款漏掉；預算與總覽的相應數字也須使用一致口徑。

### 金額與盒數範例

以下全是示意資料，不是實際親友名單或廠商報價。

| 需求來源 | 對象數 | 每個對象盒數 | 小計 |
| --- | ---: | ---: | ---: |
| 會參加婚宴的家庭 | 60 | 1 | 60 |
| 不參加但需送餅的親友 | 20 | 1 | 20 |
| 公司部門 | 5 | 2 | 10 |
| 合計 | 85 | — | 90 |

另留備用 5 盒，需準備 95 盒。若廠商確認購買 90 盒、另贈 5 盒，則可供 95 盒、缺口為零；不能對 95 盒全部收取貨款。

假設成交每盒 600 元，運費 1,500 元、額外折扣 1,000 元，確認訂購金額為 `90 × 600 + 1,500 − 1,000 = 54,500 元`。已付訂金 20,000 元，尚欠 34,500 元。即使只登記一筆已付訂金、尚未建立尾款分期，尚欠金額仍應為 34,500 元。

這筆 54,500 元在婚禮花費中只計一次。送給不出席親友的 20 盒已包含在這筆支出裡，不增加婚宴用餐人數，也不另加一遍喜餅費。

## 概念資料關係與相容性

| 概念 | 關係 |
| --- | --- |
| 送禮對象 | 可獨立存在；可人工關聯多筆既有出席回覆。第一版一筆回覆只歸到一個送禮對象，需拆送則另建獨立對象 |
| 送餅安排與明細 | 一個送禮對象可有不同款式及盒數，交付方式及日期可分批安排 |
| 喜餅款式 | 可關聯既有廠商；廠商未定時可先建暫定款式，保留需求 |
| 喜餅訂購與明細 | 連到既有廠商與唯一花費，保存成交價及贈盒；一筆訂購供應多個送禮對象 |
| 交付與交付明細 | 指向安排明細，保存當次款式及數量；實際交付可記來源訂購，總需求規劃時不強迫先逐盒分配訂購來源 |
| 付款與文件 | 使用既有花費、付款、廠商及文件的關聯 |

以新增資料承接送餅需求，保留現有 RSVP 表單、網址、出席統計與座位安排。姓名和電話用於搜尋與重複提示，不作送禮對象的唯一識別。

第一版由新人管理；現場發餅可提供精簡列印清單。若要開放線上幫手操作，再提供僅含領餅需求與交付動作的權限及 API，隱藏價格、合約、禮金與不必要地址。現有幫手角色不因新增喜餅功能而自動取得完整財務資訊。現有登入無個人帳號，紀錄經手人時可另外填名，但不宣稱已驗證該人的身分。

## 喜帖與禮金的後續擴充

紙本喜帖使用同一送禮對象與聯絡資訊，可有不同收件地址、寄送份數及進度；寄喜帖不能自動視為有送餅，送餅也不代表要寄喜帖。

禮金另建收受紀錄，可由一個或多個對象共同致贈，也可登記未出席者；一個對象可能有多筆紀錄。禮金收入獨立統計，不以禮金金額自動決定送餅盒數，也不直接沖減喜餅採購金額。

後續的補寄、致謝與對帳沿用相同對象與實際交付歷史，避免新增一套互不相連的親友名單。

## 驗收情境

| 情境 | 預期結果 |
| --- | --- |
| 從未填表的阿姨要送兩盒 | 可以直接新增；喜餅需求加二，婚宴人數與桌次不變 |
| 一家四人出席，但只送一盒 | 喜餅需求為一盒 |
| 親友改為不出席 | 盒數與已付款不變，原定現場領取需提醒改交付方式 |
| 公司部門只收餅 | 可作團體登記並填實際收件人，無須建立個人 RSVP |
| 同一戶收到兩款喜餅 | 各款分別計量與對照訂購，不能用另一款的多餘盒數掩蓋缺口 |
| 父母代領後親友再來領 | 顯示代領人、時間與已領盒數；無剩餘需求不可重複登記 |
| 兩盒先領一盒 | 保留第一次紀錄，剩餘一盒可在之後領取 |
| 宅配已寄出尚未收到 | 顯示配送中，已寄出數量不再次列入待寄送 |
| 下單後取消一戶送餅 | 需求減少、可重新安排的盒數增加；合約及付款維持原狀 |
| 廠商贈五盒 | 可供數量加五，不增加貨款 |
| 兩個家庭共用一個收件地址 | 對象不自動合併；合併配送時運費只記一次 |
| 已有喜餅花費與訂金 | 連結原花費，保留付款與附件，不另建重複支出 |
| 只登記已付訂金 | 尚欠金額仍包含未建立分期的尾款 |
| 更新款式參考單價 | 舊訂購成交單價與已付款不變 |
| 同一交付送出兩次／兩人同時操作 | 不重複扣減剩餘需求，不產生超額交付 |

## 第一版建議範圍與待確認選項

第一版完成：獨立送禮對象、從既有回覆加入、多款式盒數、地址與交付方式、分次交付及代領、訂購與廠商贈盒、預算付款串接、按用途匯出。以一款喜餅也能快速操作為預設。

待使用者補充：實際是一家一款或多家多款；是否需要幫手在線上登記領餅；是否由廠商直接宅配；第一版是否要同時加入紙本喜帖或禮金。這些選項不阻礙先確立「送餅與出席獨立、盒數與費用分開」的核心設計。
